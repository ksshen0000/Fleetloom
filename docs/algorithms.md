# Fleetloom 调度与交通算法

> 日期：2026-10-25
> 说明：路径规划（`fleetloom-traffic`）和任务分配（`fleetloom-dispatch`）用到的算法、出处和实测效果。所有算法都是公开文献中的方法，自行实现，不引入新依赖。

## 1. 路径规划

### 1.1 A* 与精确距离启发

- **搜索状态**：搜索在（点位，进入该点的边）这个状态上进行，所以转向惩罚是精确的（TRF-02）。
- **边代价**：长度 / 限速 × 权重系数，再加转向惩罚、占用惩罚和流向惩罚（见 1.2）。
- **启发函数**：从目标点沿反向边做一次 Dijkstra，得到每个点到目标的最小「长度 × 权重系数」之和，再除以车速。转向、限速和各种惩罚只会让实际代价更大，所以这个启发值不会高估，A* 仍然保证最优；它同时满足一致性。思路来自 Reverse Resumable A*：D. Silver, *Cooperative Pathfinding*, AIIDE 2005。
- **结果缓存**：每个目标点的距离表算一次，按最近使用保留 512 个目标（`RoadGraph.weightedDistance`）。

原先的启发函数是欧氏距离。在有货架、墙和单向通道的仓库布局里，欧氏距离和实际可走距离差得很远，A* 几乎退化成全图搜索。

**代价矩阵**（TRF-05，供 dispatch 选车）：每台车从所在点做一次 Dijkstra，所有目标点都确定后停止，不再对每个「车 → 点」各做一次 A*。

实测（30×30 仓库网格，有货架行和单向通道，转向惩罚 2 s/rad）：

| | 旧（欧氏启发，逐对 A*） | 新 |
| --- | --- | --- |
| 100 条随机路线 | 4623 ms | 43 ms |
| 代价矩阵 10 车 × 20 点 | 3521 ms | 14 ms |

新旧两版的路线代价逐条相同，代价矩阵逐项相同。在 60×60 的地图上，旧版平均每条路线约 1 s，新版约 0.6 ms。

### 1.2 流向感知的软代价（TRF-04 扩展）

给一台车规划路线时，其他车「还要走的那段路线」会增加代价：
- **逆向**：逆着其他车的行驶方向走同一条路径，每辆车加 `counterflowPenalty`，默认 40 s。如果那段路属于单行道（见 1.3），整条单行道的反方向都加这个惩罚，因为方向锁会锁住整段。
- **同向**：顺着其他车的方向走同一条路径，每辆车加 `followPenalty`，默认 4 s，用来把车流分散开。

这相当于优先级规划（prioritized planning）里的冲突回避代价（Silver 2005），也类似 Cohen、Uras、Koenig 提出的「高速公路」式方向偏好（*Feasibility Study: Using Highways for Bounded-Suboptimal Multi-Agent Path Finding*, SoCS 2015）。

这里没有做时空预约（如 SIPP 或 CBS）。原因是本系统的执行模型是逐段预约放行：车辆的实际到达时间受加减速、动作和通信延迟影响，时空计划很难被准确执行；而预约放行本身已经保证安全（参见 Hönig 等人 2019 年基于动作依赖图的鲁棒执行）。软代价只影响选择哪条路，不影响安全。

两个参数可在配置中调整：`fleetloom.traffic.counterflow-penalty` 和 `fleetloom.traffic.follow-penalty`，设为 0 即关闭。

### 1.3 按车型规划

- **车速**：交通模块从车辆档案（fleetloom-resource）读取每台车的车型，按「厂商/序列号」对应，30 s 刷新一次；遇到新车，最快 5 s 后重新读取。规划和代价矩阵都用该车型的最高速度。没有登记车型的车用 `default-speed`。
- **限行路径**：地图路径上的 `allowedVehicleTypes`（空表示不限）现在会生效：A*、代价矩阵和死锁退让都不走对本车型关闭的路径。车型未知的车只走不限车型的路径。启发函数不考虑限行，仍然是下界，所以 A* 仍然最优。
- **代价矩阵按车计算**：dispatch 请求代价矩阵时带上每行对应的车辆（`CostQueryDto.vehicles`），匈牙利匹配因此比较的是各车按自己速度、走自己能走的路所需的真实时间。快车离得稍远也可能先到。
- **模拟器**：虚拟车按所登记车型的最高速度行驶（场景、控制台添加和重启恢复都适用），这样仿真里各车型的差别是真实的。

演示数据见 `deploy/examples/setup-demo-fleet.sh` 和 `scenario-mixed-fleet.yaml`：
- 4 种车型：顶升（1.5 m/s）、小型顶升（2.0 m/s）、重载顶升（0.8 m/s）、叉车（1.0 m/s）。
- 货架只能由三种顶升车搬运，托盘只能由叉车搬运。
- 窄通道 WN4-WM-WS4 只对顶升和小型顶升开放，重载车和叉车要绕外环。

### 1.4 已有机制（未改动）

点位 / 路径 / 互斥区预约，逐段放行（TRF-10–13）；单行道方向锁，对向等待者优先；等待超时后的绕行（TRF-12）。

### 1.5 死锁检测与解除（TRF-15/16）

**等待图**：
- 等待预约的车，指向持有它下一段资源的车。
- 死锁解除时退到避让点、等别人先过的车，指向所有还要经过它后续路线的车。这条边是这次新加的。

**环检测**：用 Tarjan 强连通分量算法，成员多于一台的分量就是死锁。

**修复的缺陷**：以前「让行等待」不在等待图里。出现「A 退让后等 B 通过，B 等 C，C 又等 A 让出所站的点」时，这个环永远检测不到，三台车会一直不动。随机压测中，个别种子的吞吐量因此跌到正常值的 1/4。现在环里如果有让行中的车，它立即结束让行，交回正常的预约和死锁处理。

**解除方式**（未改动）：选退让距离最近的车，退到最近一个其他车用不到的空闲点。

## 2. 任务分配（DSP-04/05/06）

### 2.1 按优先级分层的全局最优匹配

原来的做法是按优先级、创建时间逐单处理，每单取离它最近的空闲车。这种贪心有一个典型问题：先到的订单拿走了离两单都近的那台车，后面的订单只能从场地另一头调车。

现在的做法：
1. 每个调度周期，把排队订单按优先级分层，高优先级先处理（DSP-06 不变）。
2. 同一优先级、同一地图内，订单和空闲车组成指派问题：代价是车到第一段任务点的空驶时间，不可行的组合禁止匹配（车型不兼容、指定了其他车、不可达等）。
3. 用匈牙利算法求总空驶时间最小的匹配：Kuhn 1955 / Munkres 1957 的匈牙利算法，采用带势函数的最短增广路形式，O(n²m)，与 Jonker–Volgenant 1987 同一路线。支持非方阵。
4. 禁止的组合换算成一个足够大的代价：先保证匹配对数最多，再在此基础上使总代价最小。
5. 电量高的车略占优，保留原先的平局规则。

这正是需求 DSP-05 中预留的「全局最优分配（匈牙利算法）」。

### 2.2 防饿死的老化项

订单多于车时，匹配会挑代价小的订单，远处的订单可能一直轮不到。为此每个订单的代价减去「已等待秒数 × `AGING_SECONDS_PER_SECOND`（1.0）」：等了 30 s 的订单，相当于近了 30 s 的空驶。这是调度里常用的老化（aging）技术。车多于订单时，每个订单都会被分到车，这一项对整行是常数，不影响结果。

### 2.3 其他改进

- **请求次数**：每个优先级 / 地图只向 traffic 请求一次代价矩阵，原来是每个订单一次。
- **测试**：`AssignmentTest` 在 500 个随机非方阵（含禁止项和负代价）上与暴力枚举对比；`DispatcherTest` 覆盖「批量匹配优于逐单就近」和「久等的订单不被饿死」两个端到端场景。

## 3. 后续可做

- **预测性分配**：把「即将完成当前订单」的车也纳入匹配，代价取其剩余时间加上从卸货点出发的空驶时间。
- **机会充电**：车辆空闲时，电量低于高阈值就去充电。这需要先调整 DSP-07 中「充电中电量低于高阈值不可接单」的规则，否则会降低可用车数。
- **死锁预防**：在预约时就避免形成环，例如按区域做银行家算法式的检查，而不是事后检测、退让。在高密度场景（每 3 个点就有 1 台车）中，死锁解除的等待仍是主要损耗。
- **运行时调参**：把两个流向参数加入控制台「系统设置」的运行时参数（目前只能通过配置文件设置）。
